## 根因
**`processor.rs::chunk_text` 用 byte offset 切片, 但 rfind('. ') 在中文 transcript 永远 None, fallback rfind(' ') + 1 切到空格后. 空格后可能是中文 (UTF-8 3 bytes), end_byte 落在中文 char 中间 → panic**.

**代码原貌 (line 514-529)**:
```rust
let mut end_byte = char_byte_offsets[end_char];

if end_char < total_chars {
    let slice = &text[start_byte..end_byte];
    if let Some(last_period) = slice.rfind(". ") {
        end_byte = start_byte + last_period + 2;        // ← byte index, 可能 +2 后落在中文中间
    } else if let Some(last_space) = slice.rfind(' ') {
        end_byte = start_byte + last_space + 1;          // ← 同上
    }
}
chunks.push(text[start_byte..end_byte].to_string());   // ← panic!
```

**复现条件**: transcript 同时含英文 ". " 序列 (例如 "2018年5月11日") + 后续中文 (例如 ". 开庭审理"). rfind('. ') 返回 last_period (英文点+空格的 byte offset), +2 后 byte 2346 在 '。' 中文句号中间 (UTF-8 bytes 2345..2348).

**§53/§55 已修的 chunk_text 是另一个函数** (chunks 切分), 不影响这里的 byte offset 处理. 但这段历史代码没被 §53 改动触及.

## 修复
`processor.rs:514-535` 加 defensive `is_char_boundary` floor:
```rust
if let Some(mut b) = candidate_byte {
    // 找到 char boundary: 向前 floor 直到 text.is_char_boundary(b) 为真.
    while b > start_byte && !text.is_char_boundary(b) {
        b -= 1;
    }
    end_byte = b;
}
```

`hard_post_process.rs::replace_range` 也加同样防御 (虽然当前调用源都安全, 防未来 regression).

## 铁律 (§169.6 立)
1. **Rust `&str[a..b]` 永远要 char boundary** — 任何 byte offset 计算后必须 `text.is_char_boundary(b)` 验证
2. **rfind 索引 + 偏移 是经典坑** — `rfind(". ") + 2` / `rfind(' ') + 1` 都可能落在 UTF-8 多字节 char 中间
3. **§53/§55 chunk_text 不代表所有切片点都安全** — 历史代码多处 byte offset, 增强防御
4. **`is_char_boundary` floor 是最稳解** — 比 manual byte arithmetic 算 char count 简单
