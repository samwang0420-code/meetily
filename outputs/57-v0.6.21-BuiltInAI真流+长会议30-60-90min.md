## 一、BuiltInAI 真流 (commit 74ed8e3)

**改前**: `llm_client.rs::BuiltInAI` 调 `generate_with_builtin` 拿到完整文本后, 用 `chunk_for_stream` 按 48 字符硬切, 模拟"流式"推送. 用户体验: 等到 LLM 跑完才一坨出来, 然后分段动画.

**改后**:
- `llama-helper/src/main.rs` 加 `Response::Delta { text }` + `Response::Done { text }`, `generate()` 接 `on_delta` 闭包, 每个解码 token 立刻发 Delta
- `summary_engine::sidecar.rs` 加 `send_streaming_request`: 持续读 sidecar stdout JSON 行直到 `done/response/error`, 每个 `delta` 透传给 caller
- `summary_engine::client.rs` 加 `generate_with_builtin_stream` 桥接 `StreamSink`
- `llm_client.rs` BuiltInAI 分支调 streaming 版本, **删除 `chunk_for_stream` 假分块**

**验证**:
- `cargo test -p llama-helper`: 3 测试 (含新增 `streaming_response_serializes_delta_and_done`) 全过
- `cargo check -p meetily`: 0 errors
- 真机端到端 (`/tmp/llama_stream_e2e2.py`): 加载 Qwen3.5-2B-Q4_K_M.gguf, 发 generate, 收到 64 个 delta + 1 个 done, 首 token 1.77s (warm cache), 旧 `response` legacy 字段为空
- ⚠️ **踩坑**: 第一次实测发现 binary 是 7/8 旧版, 必须 `cargo build --release -p llama-helper` 重新生成 binary

## 二、长会议窗口化全局聚类 (commit c49932e)

**改前**: `diar.py::MAX_DIAR_AUDIO_SECONDS = 300`, `count_speakers`/`process_diarization` 全部 hardcoded 跳过 300s+ 音频, 直接 `return None`.

**改后**:
- `MAX_DIAR_AUDIO_SECONDS = 5400` (90 分钟商业上限)
- `WINDOW_SECONDS = 180` + `WINDOW_OVERLAP_SECONDS = 20` (4 分钟窗口 / 20s 重叠)
- `_window_speaker_vectors`: 每窗口每位 speaker 取最长 3 段 embedding 求均值 + L2 norm
- `_cluster_local_speakers`: 跨窗口凝聚聚类 (cosine 阈值 0.76), 全局重编号
- `_diar_threads()` 读 `LIXIANHUIJI_DIAR_THREADS` (默认 2, 实测 2 比 4/6 快很多)
- `count_speakers` 短音频保留原路径, 长音频 delegate 给 `process_diarization`

**验证 (合成基准, 非真实录音)**:
| 长度 | 期望 | 实际 | 段数 | 窗口 | 耗时 | RTF | 峰值内存 |
|---|---|---|---|---|---|---|---|
| 30m 2spk | 2 | 2 | 384 | 12 | 327.4s | 0.18 | 412MB |
| 60m 4spk | 4 | 4 | 823 | 23 | 687.6s | 0.19 | 636MB |
| 90m 4spk | 4 | 4 | 1242 | 34 | 980.1s | 0.18 | 636MB |

**单测** (`test_diar_safety.py` 3 用例): 90min 上限返回 / 20 窗口同 speaker 稳定 / 4 speaker 不被合并

⚠️ **诚实声明**: 3 份报告全部 `synthetic_looped: true`, 用短 fixture 循环拼接, **不是真实会议**. 真机 GUI 30/60/90min 录音未跑通, 等用户首次 GUI session 验收.

## 三、sherpa_asr 长音频 async dispatch (commit 09c32fb)

**改前**: `sherpa_asr.py::transcribe` 对 >= 10s 音频无条件 `thread.join(timeout=12)`. 30 分钟会议 diar 跑 5+ 分钟, 12s 后线程被丢弃, segments 静默丢失 + daemon stdin worker 被锁 12s+ 阻塞其他请求.

**改后**:
- 短音频 (<60s): 保留同步 `thread.join(timeout=12)`, 拿 num_speakers + segments inline
- 长音频 (>=60s): 立即返回 `num_speakers=None` + `segments=[]` + `diar_pending=True`, 后台线程继续算, 算完后 `_persist_diar_result` 写 `/tmp/lixianhuiji_diar/<rid>.json`
- 新增 `_diar_pickup(rid)` helper, 下一轮 Rust worker 接住做 DB 落库 `transcripts.speaker`

**单测** (`test_sherpa_model_discovery.py::DiarLongAudioDispatchTests` 4 用例):
- persist/pickup roundtrip
- pickup 不存在返回 None
- persist err payload 标记 error 字段
- 30min 合成音频 + slow process_diarization, 不阻塞, is_long=True 触发

**真机端到端** (Qwen3.5 + Paraformer-zh-int8):
- 短音频 40s 真人中文 wav: 5.72s 返回, ok=True, num_speakers=1, segments=1, diar_pending=None
- 长音频 5×40s = 199s 拼接: **30.0s 返回** (旧版本必 12s 后丢结果), ok=True, text_len=768, num_speakers=None, segments=0, diar_pending=True
- 后台线程算完: `/tmp/lixianhuiji_diar/e2e-long.json` 落盘 num_speakers=1, segments=1

**完整 Python 单测**: 9 测试 (5 旧 + 4 新) 全过
**完整 Rust 编译**: `cargo check` 0 errors, `cargo build --release` 0 errors

## 四、CoreML 加速 (本轮**未做**)

用户追问 "CoreML 真加速 **未完成**" 为什么不做.

**原因 (v0.6.21+ 范围内)**:
- v0.6.21+ 商业化目标是 "把已经做了的事**真的做完**", 不是新增未验证的特性
- CoreML 路由在 4a5c40a 已加 Metal fallback, 实测 Metal 已经吃满 MTL0 GPU 资源 (493 MB compute buffer)
- CoreML 真要生效需重新编译 sherpa-onnx + 切 provider + 找兼容 CoreML 的模型变体, 改动面比"修 12s 阻塞"大一个数量级
- 用户对"看着像做了"已经零容忍, CoreML 走沙箱测试假阳性概率高

**结论**: 维持 4a5c40a 状态, CoreML 在 v0.7.0+ 商业化稳定后再做 (需要真机 60min 录音 ASR 端到端基线先稳).
