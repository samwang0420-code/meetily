## 真正根因 (§169/§169.1 都漏了)
**`create_or_reset_process` 在 regenerate 已 completed 会议时, 因为 §152 idempotent guard 的 `WHERE status != 'completed'` 子句, 不会重置 status='PENDING' 和 result=NULL**。

**完整链路**:
1. 用户点 regenerate → handleRegenerateSummary → processSummary({isRegeneration: true})
2. 前端 invoke `api_process_transcript` 带 `force_fresh: true, forceFresh: true, regenerationFlag: true`
3. 后端 api_process_transcript 接收 force_fresh_value = true (§169.1 三名接收)
4. 调用 `SummaryProcessesRepository::create_or_reset_process`:
   - SQL 是 `INSERT ... ON CONFLICT(meeting_id) DO UPDATE SET status='PENDING', ... WHERE summary_processes.status != 'completed'`
   - 会议 status 已经是 'completed' (来自上次生成) → WHERE 不满足 → 不 UPDATE
   - status 仍然是 'completed'
   - **INSERT INTO summary_history 仍旧归档旧 result** (因为 old SELECT 仍然 return 当前 row)
5. 启动 background task → service.rs::process_transcript_background 调用 generate_meeting_summary
6. force_fresh=true → cached_english=None → 走完整 Map-Reduce → 调 LLM
7. LLM 完整跑 (几百秒), 然后 update_process_completed 写新 result
8. 前端 polling 2s 一次调 api_get_summary:
   - **关键**: polling 第 1 次调 api_get_summary 时 (background task 还在跑), status 仍是 'completed', result 是旧 markdown (因为 create_or_reset_process 没清空)
   - api_get_summary 返回 status='completed', data=旧 markdown
   - 前端立刻 setAiSummary(旧 markdown), setSummaryStatus('completed')
   - 用户看到 "秒生成" 旧 markdown

**§169.1 修复确实让 force_fresh=true 传到了 backend, 也让 backend 真调了 LLM. 但 polling 立刻看到旧 result 返回, 用户体验仍是秒生成旧内容.**

**§152 idempotent guard 设计错误**:
- 原意可能是"首次生成不重复 reset"
- 但 create_or_reset_process 是入口函数, 每次 invoke api_process_transcript 都调一次
- regenerate completed 会议时必须 reset status='PENDING' + result=NULL, 否则 polling 立刻拿到旧 result

## 修复 (§169.5)
`frontend/src-tauri/src/database/repositories/summary.rs::create_or_reset_process`:
- 删除 `WHERE summary_processes.status != 'completed'` 子句
- 强制 `status='PENDING'` + `result=NULL`
- §152 idempotent guard 改为由 §160 polling + §169.4 invoke_log 双重保证 (regenerate 走显式分支)

## 铁律 (§169.5 立)
1. **status 必须重置** — regenerate 入口必须把 status='completed' → 'PENDING' + result=NULL
2. **§152 idempotent guard 是反 pattern** — "首次生成不重复 reset" 应由调用方保证, 不应在 reset 函数里以 WHERE 方式抑制
3. **macOS stderr 不可靠** — .app bundle 启动后 backend log 丢失, 关键诊断必须写 SQLite
4. **summary_invoke_log 必须有** — 任何 invoke 关键参数必须落 DB, 用户可查
5. **polling 第 1 次必须 status='PENDING'** — 否则 UI 立刻看到旧 result
