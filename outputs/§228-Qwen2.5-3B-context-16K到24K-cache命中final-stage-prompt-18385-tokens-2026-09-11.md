## 根因 (3 跳)

### 1. transcript 实际只有 6433 chars

`SELECT COUNT(*), SUM(LENGTH(transcript)) FROM transcripts WHERE meeting_id='meeting-b0297a12-...'` → 100 段 / 6433 chars

6433 中文 chars ≈ 9650 tokens (Qwen 2.5 BPE 中文约 1.5 token/char)

### 2. cache 命中路径不走 Map-Reduce

`processor.rs:957` `resolve_cached_english` 命中:
```rust
let (mut english_markdown, successful_chunk_count) = if let Some(cached) = resolve_cached_english(...) {
    (cached.to_string(), 1_i64)  // <-- 不调 LLM pass 1, 直接用 cached
} else {
    // single-pass or Map-Reduce
};
```

但 cache 命中后,**final stage 仍调 LLM 一次**: `generate_summary_with_stream(...)` 把 cached english summary 作为 `content_to_summarize` 注入 user prompt。

DB cached english summary 长度: **1832 chars** (b0297a12) / 1913 chars (c1299582)。

### 3. §222 token 估算严重低估中文 BPE 实际密度

§222 注释用 "0.35 token/char" 英文估算:

```
context_size: 16384, // §222 16K 装得下 chunk (max ~9K) + 800 output = ~10K
```

但 **Qwen 2.5 中文 BPE 实际 1.3-1.7 token/char**。实测 cache 命中 final stage prompt:

| Component | Chars | Tokens (×1.4 BPE) |
|---|---|---|
| 7 system consts (§138/§141/§163/§195/§161/§188/§189) | 10443 | 14620 |
| cached english summary (b0297a12) | 1832 | 2564 |
| fact_check_reminder + hotwords | ~600 | ~200 |
| max_tokens | — | 1000 |
| **TOTAL** | **12875 chars** | **~18385 tokens** |
| **n_ctx** | — | **16384** |
| **OVERFLOW** | — | **-2001 tokens** |

**实际 log 的 17954 tokens 跟估算 18385 tokens 完全吻合**。

## 铁律 (任何 v0.X 演进适用)

1. **Qwen 2.5 中文 BPE token 比率 1.3-1.7 token/char**(不是 §222 估的 0.35)
2. **任何 prompt size 估算必须实测** — §222 估的 9058 tokens 实际是 ~18000 tokens
3. **cache 命中路径 ≠ Map-Reduce 路径** — cache 命中 final stage prompt 包含全部 system const + cached summary
4. **n_ctx ≥ system_consts_tokens + max_cached_summary_tokens + max_tokens + 30% buffer**
5. **24K 是 b0297a12 真实需求的 sweet spot** — 24K 比 16K 多 8K buffer,够 cover 任何现有 prompt 组合
6. **每次改 context_size 必须同步 guard §X anchor regex** — 防 anchor fail 误报 (§56 强化)
