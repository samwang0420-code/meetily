## 2026-07-04 v0.8.35: /admin/services 性能优化 (D1 索引 + 分页 + SQL 精简)

## W2.3 (16:30) — Level 3 字级 timestamp + 按句切段

**用户反馈**:
> "很牛逼了, 1 是 SenseVoice, 2 是 Paraformer, 如果再细致点就更好了"

W2.2 修好后 127s 音频分 10 段, 但有些段把多句合并 (如 [00:41] 实际两句话合一段, [01:38] 4-5 句合一段). 用户希望更细颗粒度.

**方案**: Level 3 — 用 sherpa-onnx 字级 timestamps 按句末标点 + 停顿切 sub-segments
- 实测 `sherpa_onnx==1.13.4` SenseVoice-zh 返回 70 token × 每 token 时间戳 (精度 ~0.06s)
- Paraformer-zh INT8 不返回 timestamps (模型架构限制), 退回 W2.2 行为
- 切点规则: `。！？` 强制切 / 下一 token 时间差 > 0.5s 切 / 空格 + 0.3s 停顿切
- 过短 sub-segment (<200ms) 合并避免碎片

**4 条边界约束**(用户提的):

### 1. 时间戳传输体积控制
- 请求加 `timestamps: bool` 字段, **默认 false**
- Rust 端总是请求 `true`, 但 daemon 端只在 Pro + RAM>=8GB + 模型支持时返回
- 实际载荷: SenseVoice 4 token/s × 2h × 14B = ~400KB 单次 IPC, 可接受
- transcripts.json **不存 token 数组**, 只存段级 `{start_ms, end_ms, text}`

### 2. 长音频内存缓存优化
- daemon 返回后**立即消费** token/timestamps, 切 sub-segments 后立刻 `drop`
- 用 `std::sync::OnceLock<Mutex<Option<...>>>` 暂存当前段 (段级别, 不累积)
- 长音频峰值 = 当前段 token × 14B ≈ ~1KB, 远小于 segment.samples (25s × 64KB ≈ 1.6MB)

### 3. 兼容历史旧音频缓存
- **DB schema 不动**, transcripts 表继续存 `{start_time, end_time, text}`
- 新旧逻辑**同 schema**: 老会议 = VAD 段循环 (W2.2), 新会议 = Level 3 sub-segments
- 前端按现有渲染逻辑读, 自动兼容
- 零数据回滚风险

### 4. 低配硬件自动降级
- daemon 启动时 `sysctl hw.memsize` 检测总 RAM
- total RAM < 8GB → `level3_supported: false` → 即使 Rust 请求 timestamps=true 也**不返回**
- 总 RAM ≥ 8GB → 启用 (本机 M1 8GB Docker base 报告 8GB, 刚好通过)
- Paraformer-zh 永远 `level3_supported=false` (模型无 timestamps)

**改动 3 文件**:
- `frontend/src-tauri/scripts/sherpa_asr.py` (+60 行): `_capability()` + `timestamps` 请求字段 + token/timestamp 返回
- `frontend/src-tauri/src/audio/sherpa_daemon.rs` (+30 行): `SherpaResponse.tokens/timestamps` 字段 + `capability()` 方法 + `transcribe_blocking(..., timestamps: bool)` 签名

## 2026-07-10 15:00 · v0.6.11 实时流式识别 pipeline

**触发**: 用户原话 "我们要的就是实时输出识别内容, 这是我们最大的壁垒了"

**调研**:
- SenseVoice 是 NAR 非自回归, sherpa 1.13.4 OfflineRecognizer 不支持 modified_beam_search / streaming

1. sherpa_asr.py 加 streaming pipeline (stream_begin/chunk/finalize) — chunked offline 模拟流式
2. sherpa_daemon.rs 加 3 commands + JSON bridge
3. transcription/worker.rs Sherpa branch 推 streaming session
4. frontend livePartialText 状态 + onTranscriptPartial listener
5. 实际单测: 6s 合成音频 4 chunks, decode ~30-80ms / chunk

**结果**: PID 12271 跑通, npm 10s + cargo 1m24s ✓

**核心机制**:
- 每 600ms 跑一次累计 buffer 识别, daemon 推 partial 立刻进 context
