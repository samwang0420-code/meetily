## 1. 录音端: 17 段 ~0.2-0.3s 重叠 (非 bug)

DB 实测:
- meeting-a09de61d (谢关竹与江战关于入职及购买折叠屏手机的会议记录)
- 77 分钟 (max_end=4643.4s, sum_dur=3314.2s, sum 占 71%)
- 544 段, 分布: 79 短段 (0-2s) + 92 中段 (2-5s) + 48 (5-8s) + 325 强切段 (8.01-8.41s)
- 17 段重叠 (fail-safe s+0.1<pe), 重叠 0.19-0.28s
- 段间 344 个 0-0.5s gap (强切段之间几乎没缝隙, silero 认连续)

根因:
- 8s 强切 (§32) 正常工作 (325 段命中 8.01-8.41s 区间)
- 0.2s 重叠是 silero `pre_speech_pad / post_speech_pad` 边界 + 浮点误差
- 不是重复识别 (重叠段文字完全不同, 是相邻语音被切分边界算进下一段)

**结论**: 修复后行为, 不是 bug. 用户截图里看到的"00:00 → 00:05 → 00:07 → 00:27" 段间是真实 silero VAD 切分.

## 2. 摘要端: 前端 polling 超时 (真 bug)

DB 实测:
- summary_processes.status = **completed** ✅
- chunk_count = **9** ✅ (Map-Reduce 1800 cap 生效)
- processing_time = **1109s = 18.5 分钟**
- error 字段 = **空**
- result 字段 = 977 字符 markdown 摘要开头 "本次会议主要围绕主角谢关竹在南疆市的入职流程..."
- start_time = 2026-08-01T06:11:07
- end_time = 2026-08-01T06:29:36

**后端完美, 问题是前端 polling 10 分钟超时**:
- `frontend/src/components/Sidebar/SidebarProvider.tsx:191`
  ```ts
  const MAX_POLLS = 300; // 10 minutes at 2-second intervals
  ```
- 实际: 300 × 2000ms = 600s = 10 分钟
- 但 i18n 文案说"15 分钟":
  ```ts
  // zh.ts:543
  timeout_15min: '摘要超时 (15 分钟), 请重试或检查网络',
  // en.ts:653
  timeout_15min: 'Summary timeout (15 min), please retry or check your network',
  ```

**时间错位链**:
1. 用户点"重新生成"
2. 前端起 polling, 最多等 600s = 10 分钟
3. 后端 Map-Reduce 9 chunk × 平均 123s = 18.5 分钟
4. 前端 10 分钟时主动 `setStatus('error')` + error="摘要超时 15 分钟"
5. 后端继续跑 8.5 分钟, 最终 status=completed + result 有内容
6. 前端永远不知道后端已完成 (轮询已停), UI 永远显示"会议纪要生成失败"

**用户截图里看到的"会议纪要生成失败"就是这次**——后端实际成功了, 但前端显示错了.

## 3. 修复建议 (按 §15 §25 §37 铁律, 必须 GUI 验证)

### 3.1 前端 polling 超时延长 + i18n 同步

**Option A (推荐)**: 把 MAX_POLLS 调到 1800 (30 分钟), i18n 文案同步 30 分钟
- 文件: `frontend/src/components/Sidebar/SidebarProvider.tsx:191`
- 文件: `frontend/src/i18n/locales/zh.ts:543`
- 文件: `frontend/src/i18n/locales/en.ts:653`
- 验证: 用户重新生成摘要 (a09de61d 已 completed, 不用等 18.5 分钟),
        改用 e5b78a31 (9000 chars) 或新录 30 分钟会议

**Option B**: 后端主动 push 状态变更事件 (Tauri event 'summary-status-changed')
- 前端不轮询, 监听事件
- 工作量大, §18 后置项之一 (P3 搁置)

**Option C**: 后端拆分 Map-Reduce 为 streaming
- 每完成 1 chunk 就 emit status='chunk_done'
- 前端 UI 显示进度条
- 工作量最大, §18 后置项之一

**建议 A**, 工作量最小, 解决 95% 场景.

### 3.2 用户能看到已生成的摘要吗?

后端 status=completed + result 977 字符, **理论上用户在 meeting-details 页能直接看到**.
但用户截图显示"生成总结出错 + 会议纪要生成失败", 说明**前端报错覆盖了真实结果**.

修复:
- 用户点"重新生成"前先查 summary_processes.status
- 如果 status=completed, 直接显示 result, 不再触发重新生成
- 或者: 摘要面板加"显示上次摘要"按钮, 即使 polling 失败也能回看

### 3.3 audit_db.py 加新检测

加 metric `summary_completed_but_polling_timeout`:
- 检测 summary_processes.status=completed 且 processing_time > 600 (前端超时阈值)
- 用户实际遇到的概率 ≈ 9 chunk × 18.5 分钟 / 10 分钟 polling = 必然触发
- 加 anchor 到 `check_historical_fixes.py` 防止 i18n 文案回退
