### 完整链路
```
start_recording:
  - 生成 meeting-<uuid>
  - INSERT placeholder meetings row
  - emit recording-started { meeting_id }

worker 期间 (long audio):
  - chunks 转写时透传 meeting_id + audio_start_offset
  - sherpa_asr 长音频 async dispatch (60s 阈值)
  - 后台线程算完: 落盘 + 尝试 UPDATE transcripts.speaker
    - 若 transcripts 行还没 INSERT: updated=0 (预期)
    - 若已经 INSERT: 立即命中

stop_recording:
  - audio 流停止 + transcripts.json 保存
  - emit recording-saved 事件

前端 saveMeeting:
  - 调 api_save_transcript, 复用 meeting_id
  - Rust 端 INSERT transcripts (INSERT OR IGNORE 兼容 placeholder)
  - Rust 端 apply_diar_pickup_to_meeting 触发
  - Python 扫 pickup dir, overlap 算法 UPDATE speaker
  - 用户 UI 看到 speaker 标签 ✅
```

## 已知边界

- 应用 helper 时 spawn `python3 -c` 跑内嵌脚本, 失败 non-fatal (log_warn). 如果环境 python3 不存在, helper 静默失败, speaker 不会被回填 — 但 worker 期间如果 transcripts 已经 INSERT, 实时 UPDATE 仍命中.
- 录音中如果 sherpa_asr 算得极慢 (90 分钟会议用 30 分钟算 diar), stop_recording 后还得等几分钟 pick json 才落盘. 此时 api_save_transcript 完成后立刻 apply_diar_pickup_to_meeting 会拿不到 json. 这种情况 pickup json 在后续算完后会落到 dir, **永远不会被回填** — 这是一个已知遗留, 修法是加后台定时任务轮询. 下轮 PR.
