# §169.1 regenerate 彻底修复 (2026-08-23)

## 触发
用户报告 "还是一样的问题，点重新生成秒生成和原来一样，你要彻底修复这个问题"。
即使 §169 (ee5d30a) 已经提交，regenerate 仍"秒生成 + 内容一样"。

## 真根因 (5 跳)
1. §169 commit 在 frontend useSummaryGeneration.ts:186 用 camelCase 传 `forceFresh: isRegeneration`
2. 后端 commands.rs:349 接收 snake_case `force_fresh: Option<bool>`
3. **Tauri v2 invoke 序列化默认不自动 camelCase ↔ snake_case 转换** (§24 教训), 所以后端收到 `None`
4. `force_fresh.unwrap_or(false)` → `false` (regenerate 时本应是 true)
5. service.rs:538 force_fresh=false → cached_english 走 cache lookup → 命中 → 直接 return 旧 markdown → 秒生成

**双 root cause (都是真凶)**:
- **A. invoke 序列化** — 前端 camelCase 后端 snake_case, Tauri 2.x 不自动转
- **B. §163 推理参数固化实际未生效** — service.rs 用 `custom_openai_temperature` (仅 CustomOpenAI), Ollama/BuiltInAI 路径永远 None → llm_client.rs:289 Ollama body 完全不传 temperature → qwen3.5:2b 用 Ollama model card 默认 0.8, 输出稳定 → 即使 cache bypass 了, LLM 输出也很可能类似

## 修复 (4 项组合, 任一失效其他仍保命)

### §169.1 — Tauri v2 invoke 1:1 + 双名接收
- 前端: `force_fresh:` (snake) + `forceFresh:` (camel) + `regenerationFlag:` 三发
- 后端: `force_fresh` / `force_fresh_camel` / `force_fresh_alias` 三收 → `.or().or().unwrap_or(false)`
- 后端 log_info 打印每个参数的实际接收值 (debug 时一眼看出 invoke 丢字段)

### §169.2 — prompt 头部注入 regeneration_marker
- generate_meeting_summary 的 evidence_text 头部加 `<regeneration_marker>...</regeneration_marker>` 块
- 内容含 epoch_ms + meeting_id 后缀 → 每次 regenerate prompt 都不同
- 明确告诉 LLM "produce a fresh, alternative summary, do NOT match previous wording or structure"
- 即使 cache 命中也强制 LLM 看到 "重新审视" 指令

### §169.3 — Ollama 路径补传 temperature/top_p
- llm_client.rs:289 Ollama body options 块同时支持 num_predict + temperature + top_p
- service.rs::process_transcript_background 增加 `regeneration_flag: bool` 参数
- service.rs::generate_meeting_summary 调用前算 effective_temperature:
  - regenerate + Ollama/BuiltInAI → `Some(0.7_f32)` (介于 §163 0.1 与 Ollama 默认 0.8 之间)
  - CustomOpenAI → `custom_openai_temperature` (用户已设)
  - 首次生成 → None (走 model card 默认)
- 0.7 让 regenerate 输出明显不同于上次的版本, 但仍保留一定稳定性
