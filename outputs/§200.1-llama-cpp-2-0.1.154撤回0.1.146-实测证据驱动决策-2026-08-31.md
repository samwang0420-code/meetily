# §200.1 llama-cpp-2 0.1.154 撤回 0.1.146 — 实测证据驱动决策 (2026-08-31)

## 触发

本 session 接手时 (`main` HEAD = `7758960` §200 byte boundary panic 修复已完成), 发现 working tree 有未提交的反向改动:
- `llama-helper/Cargo.toml`: `=0.1.146` (main 上) → `=0.1.154` (未提交)
- `Cargo.lock`: 0.1.146 → 0.1.154 (未提交)

未提交原因疑似前一 session 把 §197 (commit 39b2f6d, 2026-08-30) 的回退 commit 给反向操作了, 但没 commit + 没测。

## 决策: 立即撤回 0.1.154 反向操作

**铁律驱动**: §197 已经实测过 0.1.154 升级无效, 实测数据:

| 版本 | 50 tokens decode | tok/s | Metal 路径 |
|---|---|---|---|
| 0.1.146 (回退后 §197) | 6.7s | **7.44** | ✅ Metal 全 offload, per-token decode 走 Metal |
| 0.1.154 (升级前 §196) | 4.6s/20t | 4.3 | ❌ 99.6% CPU fallback (`ggml_gemv_q4_K_8x4_q8_K`) |

**0.1.146 反而比 0.1.154 快 1.7x**！

## 根因 (为什么 0.1.154 反而慢)

llama-cpp-sys-2 0.1.154 内嵌的 llama.cpp Metal Q4_K 路径要求:
- `mul_mv_q4_K`: `ne11 >= 4` (BS 4-8)
- `mul_mm_q4_K`: `ne11 > 8` (BS > 8)

但 per-token decode 时 `ne11 = 1` (单 token 生成), **两个 Metal 路径都不满足** → fallback 到 CPU `ggml_gemv_q4_K_8x4_q8_K` → 99.6% CPU 占满。
