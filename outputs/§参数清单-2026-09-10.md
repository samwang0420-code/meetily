## 3. llama.cpp / llama-cpp-2 内核参数

**版本**: `llama-cpp-2 = 0.1.146` (Rust binding),**§197 实证最佳 baseline**
- 0.1.154 实测 per-token decode fallback CPU (4.3 tok/s),**0.1.146 全 offload Metal (7.44 tok/s)**
- 等 llama-cpp-rs 同步 llama.cpp 主仓库 b10684+ 的 Q4_K ARM/Apple Silicon GEMV 优化 PR 才能升级

**编译特性**: `--features metal` (Cargo.toml feature flag)

### 3.1 Context / Batch 参数 (`llama-helper/src/main.rs:519-541`)

```rust
n_ctx      = 16384   // §222: §217 8K 不够 chunk 2 prompt 9074 tokens
n_batch    = 16384   // §224: logical max,跟 LlamaBatch::new 第一个参数一致
n_ubatch   = 512     // §224: physical max,Metal compute buffer 不能太大
n_threads  = 6       // (8/2)+2,留 2 给 UI thread
n_threads_batch = 6
```

**n_batch vs n_ubatch 的区别** (§224 关键):
- `n_batch` = `context.n_batch` 单批 decode 上限 (logical, **LlamaBatch::new 第一个参数必须 >= n_batch**)
- `n_ubatch` = `cparams.n_ubatch` 单次 compute graph 的 physical token 上限
- GGML_ASSERT: `n_batch >= n_ubatch && n_batch % n_ubatch == 0`
- n_ubatch=N_BATCH=16384 时 worst-case Metal buffer = ~9.3 GB → M3 8GB OOM
- n_ubatch=512 (llama.cpp default H100/A100 friendly) M3 8GB 够用

### 3.2 KV Cache (§223 改回 F16)

```rust
// 当前: 不调用 with_type_k / with_type_v,走 llama.cpp 默认 F16 KV
// §223 (2026-09-10) 教训: Q4_0 KV + n_ctx=16K + Qwen 2.5 3B Q4_K 组合
//   触发 'failed to eval' (llama_decode 返回 -2 = memory init_batch 失败)
// §215 cnblogs 文章推荐 Q4_0 KV 是 4K context 场景,n_ctx=16K 不稳定
// 16K F16 KV = 0.32 GB,M3 8GB 仍剩 5.5 GB headroom ✓
```

**KV cache 容量估算** (F16, n_ctx=16384):
- Qwen 2.5 3B GQA: 8 KV heads × 128 head_dim × 36 layers × 16384 tokens × 2 bytes
- = 8 × 128 × 36 × 16384 × 2 = **~1.2 GB** (峰值)
- 但 llama.cpp lazy alloc,实际使用 ~0.32 GB per 16K context

## 4. GPU Layer Offload (§193 GQA-aware)

**调用栈** (`llama-helper/src/main.rs:308`):
```
get_default_gpu_layers(model_path, context_size=16384, n_layer=Option<36>)
  → calculate_gpu_layers(file_size=2.1GB, model_layers=36, vram_gb=4.8GB, context_size=16384)
```

**VRAM 估算** (Apple Silicon unified memory):
```rust
hw.memsize = 8 GB → detect_metal_vram() = 8 × 0.6 = 4.8 GB
safe_vram  = 4.8 × 0.85 = 4.08 GB
```

**GQA-aware per-layer 估算** (§193 关键):
```yaml
file_size_gb:    1.93
n_layer:         36
weight_per_layer = 1.93 / 36     = 0.054 GB
kv_per_layer     = 0.04 GB/1K × 16 K / 36 layers  (small GQA, §193)
                = 0.018 GB/layer (16K F16 KV,实际估算偏低因为 KV lazy alloc)
total_per_layer  = 0.054 + 0.018 ≈ 0.072 GB
safe_layers      = floor(4.08 / 0.072) = 56 → min(56, 36) = 36
n_gpu_layers     = 36 (全部 offload 到 Metal)
```

**实测**: §193 commit 之前 n_gpu_layers=0 (估算错) → 100% CPU decode (1.4 tok/s)。
§193 fix 后 → 36/36 offload → 7.44 tok/s (实测)。

## 7. 性能基线 (实测)

| 项目 | 实测值 | 来源 |
|---|---|---|
| **Per-token decode (M3 Metal)** | **7.44 tok/s** | §197 50 tokens / 6.7s |
| 单 chunk (800 tokens) | ~108s | 800 / 7.44 |
| 4 chunks (10K chars 会议) | ~7-9 min | §224 实测 |
| 38min 推理生成 9261 字符摘要 | 38min12s | §194 旧 900s timeout 失败案例 |
| Memory peak (M3 8GB) | ~4-5 GB | RSS 实测 |

**用户级反馈问题 (已知)**:
1. **MacBook Air 无风扇** → 长跑末段降频 20 tok/s (散热问题)
2. **M3 8GB 紧** → 摘要 + 录音同时跑会触发 swap (建议分开)

## 9. 等大牛诊断的关键问题

把这些点贴给大牛,请帮忙看是否最优:

1. **n_ctx=16384 + n_batch=16384 + n_ubatch=512 是否最优?**
   - n_batch % n_ubatch == 0 ✓ (16384 % 512 == 0)
   - llama.cpp default n_ubatch=512 是否对 M3 8GB 是 sweet spot?

2. **n_threads=6 是否最优?**
   - 公式 `(cores/2)+2` = 6,留 2 给 UI
   - prefill / decode 阶段都吃 threads,Qwen 3B 这种小模型可能 threads 多反而 cache thrash?

3. **temperature=0.1 + top_p=0.3 + top_k=64 是否过保守?**
   - 中文法律/医疗摘要需要严格复述,但用户实测摘要 800 token 偶尔出现 1-2 句事实编造
   - 是不是该考虑 temperature=0.0 (greedy) + 加大 rep_penalty?

4. **KV cache F16 是最优?**
   - 16K F16 = 0.32 GB,M3 8GB 余 5.5 GB
   - Q5_0 KV (16K) 大约 0.16 GB,Q4_0 KV (16K) 大约 0.08 GB
   - §223 实测 Q4_0 KV + 16K + Qwen 2.5 3B Q4_K = 'failed to eval'。是 Q4_0 KV 的精度问题还是 GGML_ASSERT 边界问题?

5. **n_gpu_layers=36 全 offload 是否最优?**
   - M3 unified memory 8GB,8 cores
   - CPU decode vs Metal decode 各适合什么场景?

6. **chunk_size=1800 + max_tokens=800 + context_size=16384 是否最优组合?**
   - 实测 10K chars 会议: chunk 4-6 个,每个 ~3 min,总 12-18 min
   - 是不是 chunk_size=2400 + max_tokens=600 更省时间?

7. **llama-cpp-2 0.1.146 是否当前最优版本?**
   - 0.1.154 实测 per-token fallback CPU,0.1.146 7.44 tok/s 是 baseline
   - 等 llama-cpp-rs 同步 b10684+ PR 升级?

8. **prefill 阶段有没有 batch=1 多 token 收益?**
   - 当前 `LlamaBatch::new(16384, 1)` last 1 是 logit 标志
   - 是否需要 `batch.add(token, i, &[0], is_last)` 改成 multi-logit batch?
